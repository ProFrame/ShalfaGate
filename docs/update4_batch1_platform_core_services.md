## Module 1 — Storage Platform

### 1. Architecture

المشكلة الحقيقية لم تكن غياب البنية التحتية — `public.storage_objects` (سجل الملفات
العام)، و`storage_can_upload`/`storage_register`/`storage_unregister`، و`putFile()` في
`src/lib/storage/index.js` كانت **موجودة بالفعل ومكتملة** منذ Update 3. المشكلة أن
`putFile()` كانت تفرض دائماً مسار Tenant-keyed (`tenants/{tenant}/{area}/{file}`)، بينما
حاويتا `employee-assets` و`employee-signatures` تتطلبان RLS مبني على مسار User-keyed
(`{user_id}/{area}/{file}`، عبر `(storage.foldername(name))[1] = auth.uid()::text`) — وهذا
بالضبط ما وثّقته الذاكرة كـ"قرار معماري مؤجل عمداً" في الجلسة السابقة. النتيجة: كود رفع
الصورة الشخصية والتوقيع في `AuthContext.jsx` كان **يتجاوز `IStorageProvider` بالكامل** —
يكتب مباشرة إلى `supabase.storage`، بلا فحص Quota أو Mime-Type، وبلا تسجيل في
`storage_objects` — وهو انتهاك حي لنفس قاعدة "لا رفع مباشر لأي Bucket" التي أضفناها في
بداية Phase 0.

**الحل المعتمد**: توسيع `IStorageProvider`/`putFile()` بمفهوم أول-درجة اسمه `pathScope`
(`'tenant'` الافتراضي، أو `'user'`) بدل اختراع خدمة موازية أو تعديل RLS الحالي (تعديل RLS
كان يعني نقل ملفات حقيقية مرفوعة سابقاً — مخاطرة أعلى بكثير لفائدة معمارية أقل). لم تُمس
أي سياسة RLS موجودة إطلاقاً.

### 2. ERD

لا جداول جديدة — `public.storage_objects` (موجود من Update 3) يبقى المصدر الوحيد. التغيير
بالكامل في طبقة التطبيق (JS) فقط.

### 3. Database

لا ترحيل SQL جديد لهذا الموديول — الحل بالكامل في `src/lib/storage/paths.js` و
`src/lib/storage/index.js`، وهذا نفسه مؤشر جيد: البنية التحتية الفعلية كانت جاهزة، والفجوة
كانت في الاستهلاك فقط.

### 4. API (تغييرات الواجهة الأمامية)

- `src/lib/storage/paths.js`: أُضيفت `userPath(userId, area, fileName)` →
  `{userId}/{area}/{fileName}` — مطابقة تماماً لما تتطلبه RLS الحاليتان لـ
  `employee-assets`/`employee-signatures`.
- `src/lib/storage/index.js`: `putFile()` تقبل الآن `pathScope` (`'tenant'` افتراضي،
  متوافق للخلف 100% مع كل مستدعٍ حالي — الدردشة، الشعارات) و`ownerId` (إلزامي فقط عند
  `pathScope: 'user'`)، وتُعيد الآن أيضاً `id` (معرّف صف `storage_objects` الذي أنشأته —
  كان يُهمَل سابقاً، واحتاجه موديول 2 مباشرة). أُضيفت `unregisterObjectsByPath(paths)`
  للإلغاء الدفعي بحث بالمسار، وأُضيفت طريقة `list(prefix)` إلى `IStorageProvider` نفسه
  (منفَّذة في الأربع تطبيقات: `supabaseProvider` تنفيذ حقيقي، `proxyProvider`/
  `disabledProvider` ترفضان صراحة برمز `LIST_NOT_SUPPORTED_FOR_PROVIDER` بدل فشل صامت،
  `localProvider` تُعيد مصفوفة فارغة) — لم تكن موجودة، واحتاجتها `AuthContext.jsx` لسرد
  مجلد المستخدم دون العودة لاستدعاء `supabase.storage` مباشرة (مخالفة صريحة لقاعدة §15).
- `src/context/AuthContext.jsx`: `uploadProfileAsset()`/`deleteProfileAsset()` أصبحتا
  تمران عبر `putFile()`/`getStorageProvider().list()`/`.remove()`/`unregisterObjectsByPath()`
  حصراً — لا استدعاء مباشر لـ `supabase.storage` متبقٍ. نفس التوقيع الخارجي، نفس أسماء
  الحقول (`avatar_url`, `signature_url`, `signature_path`).
  **ملاحظة تصحيح مهمة (اكتُشفت في المراجعة المعمارية، انظر القسم "المراجعة")**: تغيير شكل
  المسار (تعشيش تحت `{area}/`) كسر منطق تنظيف/حذف الملفات القديمة لأنه كان لا يزال يسرد
  المجلد العلوي المسطّح القديم. أُصلح بإضافة `legacyFlatPaths()` — دالة داخلية غير مُصدَّرة
  في سياق العقد — تكتسح الشكل القديم المسطّح (`{uid}/{kind}-{stamp}.{ext}`) بالتوازي مع
  الشكل الجديد المتداخل، حتى لا يبقى أي ملف موظف حقيقي مرفوع سابقاً يتيماً في التخزين، ولا
  يُبلَّغ المستخدم بنجاح حذف توقيعه بينما الملف الفعلي ما زال موجوداً.

### 5. Permissions

لا تغيير على صلاحيات RPC (لم تُعدَّل أي دالة SQL). التأثير العملي: رفع الصورة/التوقيع
أصبح يُفحص الآن مقابل `storage_policies` (نوع الـ Core: `image/jpeg, image/png,
image/webp, image/svg+xml, image/x-icon`، حتى 5MB) — تحققتُ أن حقل الرفع الفعلي في الواجهة
(`AppShell.jsx`) محدود أصلاً بـ `accept="image/png,image/jpeg,image/webp"`، فلا يوجد أي
احتمال رفض لملف كان يُقبل سابقاً.

### 6. Workflow

لا علاقة.

### 7. Storage

هذا الموديول هو نفسه Storage. القاعدة الجديدة المثبتة: **مسارَي User وTenant فقط، ولا
مسار ثالث** — أي بيانات مستقبلية (Assets، Safety، Operations) تحتاج ربط ملف بموظف بعينه
(لا بشركته) تستخدم `pathScope: 'user'`، ولا تخترع تنسيقاً جديداً.

### المراجعة المعمارية (قاعدة §16) — عُثر على Blocker حقيقي وأُصلح

مراجعة مستقلة بثلاثة محاور (Correctness/Regression، Module Ownership/Security،
Test/Convention Quality) + تحقق عدائي منفصل، **وجدت Blocker مؤكداً**: تغيير شكل المسار
(تعشيش تحت `{area}/`) ترك منطق تنظيف/حذف الصورة الشخصية والتوقيع في `AuthContext.jsx`
يسرد المجلد العلوي المسطّح القديم — فلا يجد أبداً أي ملف مرفوع بالشكل الجديد، فيبقى الملف
القديم يتيماً عند الاستبدال، ويُبلَّغ المستخدم بنجاح الحذف بينما الملف الفعلي (التوقيع
خصوصاً — بيانات حسّاسة) لا يزال موجوداً. وُجد أيضاً أن الدالتين ما زالتا تستدعيان
`supabase.storage` مباشرة بدل `IStorageProvider` (مخالفة §15).

**أُصلح**، ثم أُعيدت المراجعة بجولة تحقق عدائي منفصلة أكّدت الإصلاح — لكنها اكتشفت فجوة
حقيقية ثانية لم تكن مغطاة: الملفات الحقيقية المرفوعة **قبل** هذا التعديل (بالشكل المسطّح
القديم) ستبقى غير قابلة للاكتشاف بالمنطق الجديد وحده. أُصلحت بإضافة اكتساح للشكلين معاً
(انظر `legacyFlatPaths()` في القسم 4 أعلاه)، ثم أُعيد التحقق الكامل.

## Module 2 — Attachment Framework

### 1. Architecture

المالك: Storage Service (§12 من `bbnovix_contract.md`) — طبقة رفيعة فوق `storage_objects`
(موديول 1)، وليست تخزيناً موازياً. `storage_objects` يبقى مصدر الحقيقة لـ"أين الملف
وماذا هو" (المسار، النوع، الحجم، المزوّد)؛ الجدول الجديد `attachments` يضيف فقط ما لا
يملك `storage_objects` رأياً فيه: "هذا الملف مرتبط بهذا السجل التجاري، بهذا الترتيب،
وربما معلَّم للحذف" — دورة حياة مختلفة تماماً عن دورة حياة الملف نفسه، ولهذا جدول منفصل لا
أعمدة إضافية على `storage_objects`.

**قرار نطاق متعمَّد**: لم يُهاجَر `src/data/formsService.js`/`form_attachments` (النظام
القديم الذي يرفع مباشرة لـ `supabase.storage` بلا فحص Quota أو Mime، تماماً كما كان
`AuthContext.jsx` قبل إصلاح الموديول 1) إلى الإطار الجديد في هذه الدفعة. الفجوة حقيقية،
لكن ترحيل شاشة حية بمسارَي قراءة وكتابة هو مشروع ترحيل ميزة قائم بذاته، وليس "بناء
الإطار" — سُجِّلت في `bbnovix_contract.md` §15 (Forbidden) كبند معروف، تماماً كما سُجِّل
`FormsPortal.jsx`’s `Date.now()` سابقاً في Phase 0 بدل إصلاحه ضمن نطاق غير مخصص له.

### 2. ERD

```
public.attachments
  id (PK)  tenant_id (FK tenants)  storage_object_id (FK storage_objects, composite w/ tenant_id)
  entity_type  entity_id  display_order
  marked_for_removal  marked_for_removal_by  marked_for_removal_on
  + الأعمدة القياسية (created_by/updated_by/is_deleted/row_version/...)

  قيد فريد: (tenant_id, storage_object_id) — كل storage_object يُربَط بسجل واحد فقط أبداً
  (كل رفع حقيقي عبر putFile() ينتج صف storage_objects جديداً؛ لا إعادة استخدام).
```

### 3. Database

ملف الترحيل: `supabase/migrations/202608050040_attachment_framework.sql`.

- فهرس فريد جديد `uq_storage_objects_tenant_id` على `storage_objects (tenant_id, id)` —
  مطلوب تقنياً لأي مفتاح خارجي مركّب يستهدف هذا الزوج تحديداً (نمط موثّق مسبقاً في
  `bbnovix_contract.md` §1: "Cross-tenant references are blocked structurally with
  composite foreign keys").
- `public.attachments` بمعاملته القياسية الكاملة لجدول أعمال (tenant_id + RLS مقيِّدة +
  `apply_row_defaults`) — **ليس** بنية تحتية (على عكس `number_sequences` في Phase 0)، لأنه
  بيانات عمل حقيقية.
- **تم التحقق فعلياً**: تطبيق كامل سلسلة الـ40 ترحيلاً (39 من قبل + هذا) على نسخة
  PostgreSQL 17 معزولة نجح بلا أي خطأ، ثم اختبار وظيفي حي كامل: ربط ملفين حقيقيين بسجلين
  مختلفين، سرد المرفقات، تعليم للحذف (يبقى ظاهراً بالعلم صحيحاً — وفق قاعدة FourthUpdate.md
  الصريحة)، إلغاء التعليم، رفض محاولة ربط نفس الملف مرتين (فهرس فريد)، ورفض هجوم عابر
  للمستأجرين (موظف من شركة يحاول ربط ملف شركة أخرى → `STORAGE_OBJECT_NOT_FOUND`، وسرد
  مرفقات شركة أخرى يعيد مصفوفة فارغة).

### 4. API

RPCs (كلها `security definer`، تُنفَّذ ضمن `current_tenant_id()` الجلسة فقط — لا معامل
`p_tenant_id` إطلاقاً في هذا الموديول، فلا يتكرر تعقيد صلاحيات Phase 0):

```
attachment_attach(p_storage_object_id, p_entity_type, p_entity_id, p_display_order?) → uuid
attachment_list(p_entity_type, p_entity_id) → jsonb[]  -- يضم بيانات storage_objects مدمجة
attachment_mark_for_removal(p_id, p_marked default true) → void
```

الواجهة الأمامية: `src/lib/platformCore/attachments.js` — `attachFile()` (يرفع عبر
`putFile()` ثم يربط في نداء واحد)، `listAttachments()` (يحل الروابط الفعلية عبر
`getStorageProvider().getUrl()` — استخدم `o.layer` المُعاد من `attachment_list` وليس
تخميناً من وجود `bucket`)، `markAttachmentForRemoval()`. جميعها `{data, error}`، لا `throw`.

المكوّن المشترك: `src/components/platform/AttachmentsPanel.jsx` (مسجَّل في جدول §10
Cross-module component contract). شبكة بطاقات + معاينة كاملة الشاشة (تكبير/تصغير/تدوير
للصور فقط — بصراحة، بلا محاولة تزييف تلك الأدوات لملفات PDF/Office التي تحتاج مكتبة
Rendering غير موجودة في المشروع؛ بدلاً من ذلك "فتح"/"تنزيل" كاملان وصادقان)، طباعة، فتح في
تبويب جديد، تالي/سابق. لا استبدال ولا حذف فعلي من الواجهة — فقط تعليم/إلغاء تعليم.

### 5. Permissions

`attachment_attach`/`mark_for_removal` تتحققان من الملكية (`created_by`/`owner_id =
auth.uid()`) أو `Storage.Manage`. `attachments` RLS: قراءة لصاحب السجل أو حامل
`Storage.Manage` فقط (نفس نمط `storage_objects` تماماً — "ليست عامة داخل الشركة، من أراد
عرضها لجمهور أوسع يبنيها عبر RPC خاصة به وفحص جمهور خاص به").

**تصحيح حرج (Blocker مؤكد، انظر "المراجعة المعمارية" أدناه)**: `attachment_list()` كما
كُتبت أول مرة كانت تكتفي بفحص `tenant_id` فقط — أي موظف مصادَق داخل نفس الشركة كان يستطيع
قراءة مرفقات أي سجل آخر (حتى لو لم يكن هو من رفعها) بمجرد معرفة `entity_id`، لأن
`SECURITY DEFINER` يتجاوز RLS الجدول تماماً، فتصبح شروط WHERE داخل الدالة نفسها هي الحد
الفعلي الوحيد — لا سياسة RLS الموصوفة أعلاه. أُصلح بإضافة نفس شرط الملكية
(`a.created_by = auth.uid() or o.owner_id = auth.uid() or has_permission('Storage.Manage')`)
داخل WHERE مباشرة، مطابقاً تماماً لما تفعله `attachment_attach`/`mark_for_removal` أصلاً —
لم يكن نقصاً في التصميم، بل نسيان تطبيقه على مسار القراءة تحديداً.

### 6. Workflow

لا تكامل بعد — جاهز لأي موديول مستقبلي (Assets، Safety، Operations، أو ترحيل النماذج
لاحقاً) يحتاج "قائمة ملفات مرفقة بسجل".

### 7. Storage

هذا الموديول **هو** طبقة استهلاك التخزين للمرفقات تحديداً. لا Bucket جديد، لا مزوّد جديد —
يستخدم `putFile()`/`storage_objects` من الموديول 1 بالكامل.

### المراجعة المعمارية (قاعدة §16) — Blocker ثانٍ في هذه الدفعة، أُصلح وأُعيد التحقق

مراجعة مستقلة بثلاثة محاور (Database Correctness، Frontend Integration، Component Quality)
+ تحقق عدائي منفصل، **وجدت 8 ملاحظات مؤكدة**، أهمها:

1. **Blocker** — ثغرة IDOR حقيقية في `attachment_list()` (موصوفة في القسم 5 أعلاه). أُصلحت
   وأُعيد التحقق منها بمحاكاة هجوم حقيقية على قاعدة بيانات معزولة: زميل عمل فضولي داخل نفس
   الشركة يحاول قراءة مرفق خاص برفعه موظف آخر → يحصل على مصفوفة فارغة بدل الملف، ومحاولته
   ربط نفس الملف بسجل آخر يُرفض بـ`PERMISSION_DENIED` (فحص `attachment_attach` الأصلي ما
   زال يعمل بشكل صحيح).
2. **رئيسية** — `putFile()` (ملف الموديول 1) كانت تتجاهل خطأ `registerObject()` بصمت،
   فيُبلَّغ المستدعي بنجاح مع `id: null` بينما الملف الفعلي رُفع لكن بلا تسجيل في السجل ولا
   محاسبة Quota. أُصلحت: عند فشل التسجيل، يُحذف الملف المرفوع فوراً (Rollback) وتُعاد رسالة
   الخطأ الحقيقية بدل نجاح مضلِّل.
3. **بسيطة** — البطاقة لم تكن تعرض "رفعه فلان" رغم وجود مفتاح ترجمة له ورغم أن التعليق
   الأصلي في الترحيل يذكره صراحة. أُصلحت بإضافة `join public.users` داخل `attachment_list()`

## Module 3 — QR / Barcode Service

### 1. Architecture

المالك: Platform Core. النطاق الفعلي كان أصغر مما بدا: مولّد QR كان موجوداً بالفعل
(`qrcode.react` داخل `VerificationQr` في `VerifiedSeal.jsx`) لكنه غير قابل لإعادة
الاستخدام — ألوان ثابتة، ومحوَّل قيمة (`verifyUrl`) مدمج داخل نفس المكوّن الخاص بالتحقق.
مولّد الباركود لم يكن موجوداً إطلاقاً، ولا توجد أي مكتبة باركود في `package.json`.

**القرار**: استخراج مكوّن QR عام (`EntityQrCode`) يقبل أي `value` نصية بلا افتراضات حول
مصدرها، وإعادة بناء `VerificationQr` فوقه (بنفس الشكل الخارجي والألوان تماماً — لا تغيير
بصري) بدل ترك تطبيقين للـQR. للباركود: بناء مُرمِّز Code 128 (Set B) ذاتي كامل بدل إضافة
تبعية npm جديدة — لأن **جدول الأنماط (106 قيمة) نُقِل من الذاكرة وكان يحمل مخاطرة حقيقية
لو كان خاطئاً (باركود يبدو صحيحاً بصرياً لكن يفشل عند المسح فعلياً وبصمت)**، فتم التحقق منه
صراحة مقابل مصدر مستقل (Wikipedia، جدول Code 128 المنشور رسمياً) قبل استخدامه — تطابق تام
مع الجدول المحفوظ مسبقاً. خوارزمية الـchecksum (وزن تراكمي mod 103) تحققت أيضاً مقابل وصف
مستقل للمعيار. Set B فقط (لا A ولا C) — يغطي كل ما يخرج من `generate_number()` (حروف كبيرة،
أرقام، شرطات) بالكامل، فلا حاجة للتعقيد الإضافي.

### 2/3. ERD / Database

لا تغيير على قاعدة البيانات إطلاقاً — الموديول بالكامل واجهة أمامية.

### 4. API

```js
encodeCode128B(text) → { values, widths, error }
code128Bars(widths, moduleWidth) → { bars, totalWidth }
```

  محقَّق بخطوة بخطوة لمدخلين مختلفين، رفض حرف خارج Set B، رفض قيمة فارغة، وتحقق هندسي دقيق

`node_modules`: `level='L'` لا `'M'`، `fgColor='#000000'` لا `'#0b1b2b'`، بلا هامش — أي احتمال
فشل مسح أعلى فعلياً لوثيقة مطبوعة حقيقية).

**أُصلح**: استبدال `QRCodeSVG` بـ`VerificationQr` مباشرة (نفس النمط: `code` بدل `value`

أن ملفاً واحداً فقط (`EntityQrCode.jsx`) يستورد المكتبة الآن. تحقق تفاعلي إضافي في متصفح حي:
تسجيل دخول تجريبي حقيقي، فتح نموذج "مذكرة داخلية"، والضغط على "معاينة وطباعة" — نفّذت

سينتج شاشة خطأ حمراء، لا حوار طباعة أصلي).

**درس من هذا الموديول**: عند توحيد خدمة موجودة (QR) خلف واجهة واحدة، لا يكفي البحث عن
"أين تُستخدم الآن؟" في الملف الذي تعرفه (`VerifiedSeal.jsx`) — يجب `grep` شامل للمكتبة

كقرار لا كتكرار سهو.

**قرار الصلاحيات (معاكس عمداً لنموذج Attachments/Timeline، ومُسبَّب صراحة)**: الوسم تصنيف
خفيف، وليس محتوى حساساً كملف مخزَّن أو سجل تاريخي — فأي عضو مصادَق في الشركة يستطيع

الأكثر تحفظاً، موثَّق بوضوح في تعليق الترحيل حتى لا يُقرأ كسهو عند المراجعة القادمة.
